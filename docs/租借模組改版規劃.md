## 0. 需求原文與現況落差

| # | 需求 | 現況 | 落差 |
|---|------|------|------|
| 1 | 租借日期可以填寫 | `rentals.borrow_date` 欄位存在，但建立時**只能由資料庫 `DEFAULT now()` 帶入**，前端建立表單完全沒有日期欄位，API 也不接受外部傳入 | 使用者無法補登「其實是幾天前就借出」的情境（例如事後補單） |
| 2 | 歸還裝置表單新增範本，不同設備種類 checklist 不同，且可維護綁定；且歸還要改成「借用人先回報 → 保管人再核對」兩階段流程，順便支援借用人用手機當場填里程/定位/照片 | 歸還清點清單是**寫死在前端的 5 個固定項目**，Excel 匯出也對應這 5 欄寫死；且**只有保管人/管理員能操作歸還**，借用人完全無法參與、也無法在當下（例如車輛剛停好時）記錄里程、地點、拍照存證 | 所有設備類別共用同一份清單，無法依 iPad / iPhone / Mac / 車輛等分類客製化，也沒有任何維護介面；歸還資訊只能靠保管人事後回想或補問借用人，容易失真 |
| 3 | 依裝置種類在租借選取時跳出注意事項 dialog，同意／不再顯示，且可維護綁定 | **完全不存在**此功能 | 目前借用流程沒有任何「使用須知 / 注意事項」的告知與同意機制 |
| 4（行政新增需求） | 車輛類資產「逐日追蹤」：跨日租借需說明原因，且每天各自要有一份 checklist（例如每天記一次里程），不是只在最終歸還時一次補齊 | 借出日期/預計歸還日期沒有任何天數關聯性檢查，也沒有「每日回報」這種跟歸還分開的動作 | 車輛可能被登記成橫跨多天的一筆租借卻只有一次歸還紀錄，導致里程無法逐日歸屬、對帳困難 |

## 1. 確定方向（已與使用者討論拍板）

| 決策點 | 結論 |
|---|---|
| 改版名稱 | **租借 2.1：借還規範化** |
| 借出日期可填範圍 | 不限制（前後皆可填，之後有濫用問題再加限制） |
| 借出日期鎖定時機 | 只在**建立當下**可填，送出後鎖定不可再改 |
| 一批混多分類的歸還清點 | **合併聯集**顯示（涉及分類的清單項目取聯集，key 重複自動去重） |
| Excel 匯出清點欄位 | **動態欄位聯集**（掃描匯出範圍內出現過的所有範本項目當欄位） |
| 注意事項 dialog 觸發時機 | **提交申請時**統一跳出，列出這批所有涉及分類的注意事項，需全部同意才能送出 |
| 分類綁定繼承 | **需要**——父分類設定的範本/注意事項，子分類沒有個別設定時自動套用 |
| 維護權限 | 沿用現有「資產管理者」（`asset` 模組 `manager` 等級） |
| 檢查清單項目型別 | **不只打勾**——每個項目要能選型別：勾選（boolean）／文字（text）／數值（number）／定位（location）／**照片（photo）**，例如「里程數」「歸還地點」「車輛外觀拍照存證」 |
| 歸還流程 | 改為**兩階段**：借用人（或管理員代填）先回報 → 保管人（或管理員）核對後才算正式歸還 |
| 第一階段（借用人回報）觸發權限 | 借用人本人 或 管理員都可以 |
| 借用人回報 vs 保管人核對 | **分開保留兩份紀錄**（`return_checklist_reported` 原始回報 / `return_checklist` 核對後最終版），方便日後稽核比對 |
| 定位失敗（拒絕權限／裝置無 GPS）備援 | 退回讓使用者手動輸入地址文字 |
| 照片儲存方式 | 內容存資料庫（沿用既有設定描述檔的作法），**不**塞進 `return_checklist` JSON 本身，另開一張表存二進位內容，JSON 裡只存參照 ID；前端上傳前先在瀏覽器端壓縮/縮圖，避免手機原始檔案（動輒 5-10MB）直接進資料庫 |
| 車輛「一日一計」規則定義（v2，取代下面已劃掉的初版） | ~~每筆租借必須當日借、當日還，跨日直接擋~~ → **允許跨日**（例如 9/18～9/20 一次借 3 天），但建立時**必須填一欄說明**；跨日期間**每一天各自要有一份 checklist**（例如每天各記一次里程），不是只在最終歸還時補填 |
| 建立申請時的驗證 | 選到套用此規則的分類、且預計歸還日期 > 借出日期（橫跨多天）時：**允許建立，但 `reason` 欄位必填**，否則 400 拒絕 |
| 每日 checklist 的填寫時機 | **當天實際發生時當天填**（不是最後一次補齊 3 天），需要新增一個「每日回報」動作，跟「歸還」是兩件事：回報不會改變租借狀態、裝置仍在借用人名下；只有最後一天的回報才會接著觸發正式的「我要歸還」（兩階段流程） |
| 實際歸還晚於原訂計畫的處理 | **不硬擋**——若核對時發現實際歸還晚於預計歸還日期（不論原本是單日還是跨日訂單），仍允許完成歸還，但**強制要求填一欄逾期原因**，供事後查閱 |
| 規則綁定方式 | 沿用分類綁定 + 繼承機制（跟檢查清單範本、注意事項同一套邏輯），只掛在需要的分類（如車輛）上 |

## 2. 資料模型設計

> 編號說明：`fix/smtp-tls-internal-ca` 這條無關的修復分支先佔用了 `027`，所以這裡從 `028` 開始，避免合併時 migration 編號衝突。

新增 migration `027_category_rental_rules.up.sql`（Phase 1 用，先建表，維護 UI 隨 Phase 1 一併做，因為只是一個開關）：

```sql
-- 分類是否需要「逐日追蹤」（僅車輛等特定分類會開啟）：跨日租借要填說明、
-- 且每天各自要有一份 checklist 回報。與 checklist_templates / category_notices
-- 共用同一套分類繼承查找邏輯。
CREATE TABLE category_rental_rules (
    category_id            UUID PRIMARY KEY REFERENCES categories(id) ON DELETE CASCADE,
    daily_tracking_required BOOLEAN NOT NULL DEFAULT FALSE,
    updated_by             UUID REFERENCES users(id),
    updated_at             TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 逐日回報：daily_tracking_required 分類的租借，借用人（或管理員）每天各填一份，
-- 跟「歸還」是兩個動作分開存——回報不影響 rentals.status，裝置仍在借用人名下。
-- 最後一天的回報搭配另外呼叫「我要歸還」才會真的進入兩階段歸還流程。
CREATE TABLE rental_daily_reports (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    rental_id    UUID NOT NULL,   -- 對應 rentals.id（一批裡的某一件裝置）
    report_date  DATE NOT NULL,   -- 伺服器算出的「今天」，不接受前端傳入，避免補登
    checklist    JSONB NOT NULL,  -- 結構與 return_checklist 相同（同一份範本）
    reported_by  UUID REFERENCES users(id),
    reported_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (rental_id, report_date)  -- 同一天不能回報兩次
);
```

新增 `rentals.multi_day_reason TEXT NOT NULL DEFAULT ''`（建立跨日租借時的必填說明；跟後面 Phase 2b 的 `cross_day_reason` 是不同時機的不同欄位，一個是「建立時計畫跨日」，一個是「歸還時發現超過計畫」）——這欄跟著 Phase 1 的 `rentals` 異動一起加，放進同一支 migration：

新增 migration `028_rental_checklist_and_notices.up.sql`：

```sql
-- 歸還檢查清單範本（依分類綁定，支援繼承）
CREATE TABLE checklist_templates (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    category_id UUID UNIQUE REFERENCES categories(id) ON DELETE CASCADE, -- NULL = 全域預設範本
    items       JSONB NOT NULL, -- 見下方 items 結構說明
    updated_by  UUID REFERENCES users(id),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

`items` 陣列每個項目的結構（支援三種型別，不再只有打勾）：

```jsonc
{
  "key": "mileage",           // 唯一識別，存進 return_checklist 時的欄位名
  "label": "里程數",           // 顯示文字
  "type": "number",            // "boolean" | "text" | "number" | "location" | "photo"
  "required": true,            // 是否為必填，未填/未勾不能完成歸還
  "unit": "km"                 // 選填，僅 number 型別使用，顯示用（如「km」）
}
```

- `type: "boolean"` → 渲染成打勾框，存 `true`/`false`。
- `type: "text"` → 渲染成文字輸入框，存字串（例如「配件備註」）。
- `type: "number"` → 渲染成數字輸入框，存數字（例如「里程數」「電池健康度 %」）。
- `type: "location"` → 渲染成「📍取得目前位置」按鈕，呼叫瀏覽器 Geolocation API 抓經緯度，存 `{"lat":..,"lng":..,"accuracy":..,"capturedAt":"..."}`；同時顯示一個可直接開 Google 地圖的連結方便保管人核對。若使用者拒絕授權定位、或裝置沒有 GPS（例如 Wi-Fi 版平板）導致抓取失敗，**退回讓使用者手動輸入一段地址文字**，存成 `{"address":"..."}`（跟座標格式共用同一個 key，前端渲染時判斷物件內是 `lat/lng` 還是 `address` 即可）。這個型別就是用來解決「歸還地點」需求的，只掛在需要的分類（如車輛）上，不需要的分類完全不會出現這個欄位。
- `type: "photo"` → 渲染成「📷 拍照/上傳照片」按鈕（手機瀏覽器 `<input type="file" accept="image/*" capture="environment">` 可直接開相機），可設定 `"maxCount"`（選填，預設 1，例如車輛外觀要求 4 張）。上傳前**先在瀏覽器端壓縮/縮小尺寸**（例如限制最長邊 1600px）再送出。`return_checklist` 裡該 key 只存照片參照 ID 陣列 `["photo-uuid-1","photo-uuid-2"]`，實際二進位內容存進獨立的 `checklist_photos` 表（見下方），避免每次讀清單列表都要撈一堆二進位資料。
- 「必填」判定：`required:true` 的項目——boolean 必須是 `true`，text/number/location/photo 必須有填值（photo 至少一張）——全部滿足才能送出；`required:false` 的項目可以留空。

```sql

-- 歸還清點的照片（type:"photo" 項目上傳的內容），內容直接存資料庫，
```

再新增 migration `029_rental_two_stage_return.up.sql`（獨立一支，因為改的是 `rentals` 表本身，跟上面分類綁定的表無關）：

```sql

ALTER TABLE rentals ADD COLUMN IF NOT EXISTS cross_day_reason TEXT NOT NULL DEFAULT '';

-- 資產「最後歸還位置」——與 assets.location（管理者手動填的存放地點）分開，
-- 不互相覆蓋。第二階段核對完成時，若最終 checklist 裡有 location 型別的項目，
-- 就寫回對應資產這兩欄，下次有人挑選這台資產租借時可以看到。
ALTER TABLE assets ADD COLUMN IF NOT EXISTS last_return_location JSONB; -- {"lat":..,"lng":..,"accuracy":..} 或 {"address":".."}
ALTER TABLE assets ADD COLUMN IF NOT EXISTS last_return_at       TIMESTAMPTZ;
```

**繼承查找規則**（範本、注意事項、逐日追蹤規則三者共用同一套邏輯）：從資產的 `category_id` 開始，沿 `categories.parent_id` 往上找，遇到第一個「有自己設定」的分類就採用；一路到根都沒有，範本就退回 `category_id IS NULL` 的全域預設，注意事項與逐日追蹤規則則視為「這個分類沒有設定，不套用」。這段邏輯寫成後端一個共用 helper（例如 `resolveCategoryBinding(ctx, categoryID, lookup func(id) (*T, bool))`），三種查詢各自傳入對應的 repo 查詢函式重用。

**用不到獨立表存合併結果**：一批（`rental_number`）裡的裝置分類都各自往上找到自己的範本／注意事項後，在應用層（後端組 API 回應，或前端組 dialog 內容）把多筆結果按 `key`／`category_id` 去重聯集即可，不需要為「合併後的清單」再建一張表。

`rentals.return_checklist JSONB` 結構不變，key 從固定 5 個變成該次聯集範本的 key，本來就是自由 JSON，完全相容既有欄位與既有歷史資料。

## 3. API 與前端變更

### 3.1 借出日期（Phase 1）

- `POST /api/rentals` body 新增 `borrow_date`（格式同 `expected_return`：`"2006-01-02"`），有值就用它，沒有維持 `DEFAULT now()`。
- `RentalRepo.Create` 的 INSERT 補上 `borrow_date` 欄位。
- `Rentals.tsx` 建立表單「借用人」旁新增「借出日期」`<input type="date">`，預設今天。

#### 3.1.1 車輛逐日追蹤規則（Phase 1 一併做）

- 新增 `category_rental_rules` CRUD：`GET/PUT /api/categories/{id}/rental-rule`（`PUT` 設定 `daily_tracking_required`）。
- `Categories.tsx` 葉節點分類旁加一個簡單的 toggle「逐日追蹤（跨日租借需說明，且每天各填一份清點，供里程記錄使用）」，這個開關很單純，不像檢查清單範本/注意事項需要複雜編輯 UI，Phase 1 就能一起做完，不用等 Phase 2a。
- `POST /api/rentals` body 新增 `multi_day_reason`（選填字串）。建立時：對 `body.AssetIDs` 逐一解析其分類的 `daily_tracking_required`（含繼承），只要有任一資產屬於此類分類，且 `body.ExpectedReturn` 的日期晚於 `body.BorrowDate`（橫跨多天）：
  - 若 `multi_day_reason` 為空，回傳 400「OO 為逐日追蹤分類，跨日租借需填寫說明」。
  - 通過驗證則正常建立，`multi_day_reason` 存進 `rentals.multi_day_reason`。
- 前端：選到套用此規則的資產、且使用者把預計歸還日期改成跟借出日期不同天時，才顯示「跨日說明」文字框（平常單日租借不會看到這欄，介面不會多餘）。

#### 3.1.2 每日回報（Phase 1 一併做，因為跟建立規則綁在一起才有意義）

- 新增 `POST /api/rentals/{id}/daily-report`：
  - 權限：`rental.borrower_id == 當前使用者` 或 管理員。
  - 前置條件：`rental.status == 'active'`，且其分類經解析為 `daily_tracking_required`（不是這類分類的話直接 404，這支端點不存在給它們用）。
  - `report_date` 一律用伺服器目前日期（`CURRENT_DATE`），不接受前端傳入，避免補登/造假；已經回報過今天的話回傳 409。
  - body 帶 `{checklist}`，結構跟歸還清點共用同一套動態範本（`GET /api/checklist-templates/resolve` 解析出來的項目，例如當天里程）。
  - 寫入 `rental_daily_reports` 一列，**不改變** `rentals.status`，裝置照樣顯示在借用人名下。
- `Rentals.tsx`：`active` 狀態且屬於逐日追蹤分類、今天還沒回報過的租借，顯示「今日回報」按鈕（跟「我要歸還」是兩個按鈕並存，最後一天借用人兩個都要按：先今日回報記錄當天里程，再按我要歸還進入兩階段流程）。
- 保管人核對歸還時（Phase 2b 的核對 dialog），若該租借屬於逐日追蹤分類，額外顯示一段「每日回報紀錄」唯讀列表（撈 `rental_daily_reports` 依日期排序），方便核對每天數字有沒有異常，最終送出的 `return_checklist` 仍然只針對「歸還當天」這一份（即 `submit-return` 當下順便寫入當天的 `rental_daily_reports`，兩者資料一致）。

### 3.2 歸還清單範本（Phase 2）

- 新增 `checklist_templates` 的 CRUD：`GET/PUT /api/categories/{id}/checklist-template`（`PUT` 覆寫整組 `items`；沒有資料表示尚未個別設定，前端顯示「目前套用上層/預設範本」）。
- `Rentals.tsx` 的 GET `/api/rentals` 回應需要補上每筆的 `category_id`（`RentalRepo.List` 的 SELECT join `categories`）。
- 新增 `GET /api/checklist-templates/resolve?category_ids=a,b,c`：後端依繼承規則各自解析後聯集回傳，前端點「歸還」時呼叫這支，依每個項目的 `type` 動態渲染對應的輸入元件（取代現在寫死的 5 個 checkbox）：
  - `boolean` → `<input type="checkbox">`
  - `text` → `<input type="text">`
  - `number` → `<input type="number">`（有 `unit` 就在旁邊顯示單位文字，如「km」）
  - `photo` → 「📷 拍照/上傳照片」按鈕，選取後先在前端壓縮/縮圖，再以 `multipart/form-data` 呼叫 `POST /api/checklist-photos`（body 帶 `rental_id`、`item_key`、檔案），拿回 photo ID 塞進該 key 的陣列裡；已上傳的照片顯示縮圖，可個別移除重傳。
  - 「確認歸還」按鈕的可按條件，從現在的「五個都打勾」改成「所有 `required:true` 的項目都已填值／打勾」（photo 型別視為「至少一張」）。
- `Categories.tsx` 葉節點分類旁加「編輯歸還清單」按鈕 → dialog 可增刪排序 `items`，每項可選型別（勾選／文字／數值／定位）、是否必填、（數值型）單位，顯示「未設定時套用：OO（上層分類名或『全域預設』）」。
- Excel 匯出：`handleExport` 改成先掃過本次匯出範圍所有 `return_checklist`（保管人核對後的最終版本）出現過的 key 動態產生欄位；欄位值依原始型別呈現——boolean 是 `true` 才顯示「V」，text/number 直接印出原始值（數值型有 `unit` 就串在後面，如「12345 km」），location 印出地址或「緯度,經度」文字。

#### 3.2.1 歸還兩階段流程

現有 `POST /api/rentals/{id}/return`（單一步驟、只有保管人/管理員能按）拆成兩支：

- **`POST /api/rentals/{id}/submit-return`（新增，第一階段）**
  - 權限：`rental.borrower_id == 當前使用者` 或 管理員（比照現有 `canApprove` 邏輯，但這裡不含一般保管人）。
  - 前置狀態必須是 `active`。
  - body 同現在的 `{checklist, notes}`，`checklist` 依 `GET /api/checklist-templates/resolve` 拿到的動態範本填寫（含 `location` 型別項目，前端呼叫 Geolocation API 取得座標或退回手動地址）。
  - 寫入 `return_checklist_reported`、`return_reported_by`、`return_reported_at`，狀態改為 `pending_return`。**不清空** `assets.current_holder`（裝置實體還沒確認交還）。
  - 若該租借屬於「逐日追蹤」分類（3.1.2），這一步**同時視為當天的每日回報**，一併補一筆 `rental_daily_reports`（沒有的話補上，已經回報過當天就跳過），確保「歸還當天」也留有一筆每日紀錄，不會因為當天直接走歸還流程就漏記那天的里程。
  - 通知保管人「有一筆待核對的歸還」（沿用現有 email 通知機制，比照 `SendRentalReturned` 新增一支 `SendRentalPendingVerification` 樣板）。
- **`POST /api/rentals/{id}/return`（沿用既有路徑，語意改為第二階段「核對」）**
  - 權限不變：`canApprove`（保管人本人或管理員）。
  - 前置狀態從 `active` 改成 `pending_return`。
  - 前端「歸還核對」dialog 預先帶入 `return_checklist_reported` 的值（可修改），保管人確認/修正後送出。
  - 若該租借屬於逐日追蹤分類，且今天（`actual_return`）晚於 `rentals.expected_return`：body 需帶 `cross_day_reason`，沒有的話回傳 400；有的話寫進 `rentals.cross_day_reason`（沿用同一套「不硬擋、但要留紀錄」邏輯，不管原單是單日還是跨日訂單都適用）。
  - 寫入 `return_checklist`（最終版）、`return_notes`、`return_verified_by`、`actual_return=now()`，狀態改為 `returned`，並清空 `assets.current_holder`（沿用現有邏輯）。
  - **順便更新資產最後位置**：掃描最終 `return_checklist` 裡型別是 `location` 的項目（通常最多一個），若有值，對這批租借涉及的每個 `asset_id` 執行 `UPDATE assets SET last_return_location=$1, last_return_at=now() WHERE id=$2`。這一步只影響 `last_return_location`/`last_return_at` 這兩個新欄位，完全不動既有的 `assets.location`（管理者手動維護的存放地點）。
- `Rentals.tsx` 新增：
  - `active` 狀態下，若 `rental.borrower_id === user.id` 或 `isAdmin`，顯示「我要歸還」按鈕觸發第一階段 dialog（含 Geolocation 呼叫）。
  - `pending_return` 狀態下，`canApprove(g)` 的人看到「核對歸還」按鈕，開啟預帶借用人回報值的核對 dialog。
  - 狀態徽章（`statusConfig`）新增 `pending_return: "待核對"`。

#### 3.2.2 下次租借時看到資產最後位置

- `AssetPicker.tsx` 目前呼叫的 `/api/rental-pickable-assets`、`/api/pickable-assets` 回應補上 `last_return_location`／`last_return_at`。
- `AssetPicker` 的每張資產卡片，若該資產有 `last_return_location`，顯示一行「📍 最後位置：{地址或「開啟地圖」連結}（{last_return_at 日期}）」，讓選車的人一眼看到車子上次停在哪。沒有這筆資料的資產（多數非車輛類）完全不顯示這行，不會造成介面雜訊。
- 同樣的資訊也可以在 `AssetList.tsx` 資產詳情/ 展開列顯示（非必要，Phase 2 先做 `AssetPicker` 這個最直接需要的地方，`AssetList` 可視情況一併加上）。

### 3.3 分類注意事項（Phase 3）

- 新增 CRUD：`GET/PUT /api/categories/{id}/notice`。
- 新增 `GET /api/category-notices/resolve?category_ids=a,b,c&user_id=me`：依繼承規則解析各分類注意事項，並比對 `category_notice_acks` 濾掉「已同意且內容沒變」的分類，只回傳「還需要跳出來確認」的清單（可能是空陣列 = 不用跳 dialog）。
- `Rentals.tsx` 送出「提交申請」時，先呼叫上述 resolve API；若回傳非空，攔截提交、跳出彙整 dialog（逐項列出注意事項內容 + 一個「我已閱讀並同意」勾選），全部勾完才能繼續，按下同意後才真的送 `POST /api/rentals` 並同時呼叫 `POST /api/category-notice-acks` 寫入同意紀錄。
- `Categories.tsx` 葉節點分類旁加「編輯注意事項」按鈕 → textarea 編輯內容，同樣顯示「未設定時套用：OO」。

## 4. 執行順序

Phase 2 內容較多，拆成三個子階段個別開分支/PR，避免單一 PR 過大難以檢視：

| 階段 | 內容 | 狀態 |
|---|---|---|
| Phase 1 | `borrow_date` 可填寫（建立時，不限範圍，送出後鎖定）+ `category_rental_rules`（逐日追蹤開關）+ 跨日建立需說明 + 每日回報 API/按鈕 | **下一步：開始實作** |
| Phase 2a | `checklist_templates` 表（含 boolean/text/number/location/photo 五種型別）+ `checklist_photos` + 繼承解析 + `Categories.tsx` 維護 UI + 動態歸還清點渲染 + 動態 Excel 匯出欄位（此階段歸還仍是現有的單步驟，只是清單內容變動態） | 待 Phase 1 完成後 |
| Phase 2b | 歸還改為兩階段（`submit-return` 借用人回報 / `return` 改為保管人核對），新增 `pending_return` 狀態、`return_checklist_reported`/`cross_day_reason` 等審計欄位、借用人自助歸還按鈕、待核對通知信、核對畫面顯示每日回報紀錄 | 待 Phase 2a 完成後 |
| Phase 2c | `assets.last_return_location`/`last_return_at`，核對完成時回寫，`AssetPicker` 顯示資產最後位置 | 待 Phase 2b 完成後 |
| Phase 3 | `category_notices` + `category_notice_acks` + 繼承解析 + 提交前彙整同意 dialog + 維護 UI | 待 Phase 2c 完成後 |
| Phase 4（構想記錄，範圍與風險都跟前面不同，暫不排入本次時程） | 遺失模式自助小工具：管理員在內網把裝置設成遺失模式後，該裝置目前的借用人（仍在公司/VPN 範圍內）可以在一個限縮功能的頁面上，只看到「播放聲音」「取得目前位置」兩個安全指令按鈕，不開放 `Commands.tsx` 的完整指令列表（`eraseDevice`/`lockDevice` 等危險指令不在範圍內） | 備忘，之後有空再細部設計 |

每個 Phase 各自開一支分支、一個 PR，Docker 跑 `go build/vet/test`、前端跑 `tsc -b && vite build` 驗證後再推送，比照既有開發慣例。
